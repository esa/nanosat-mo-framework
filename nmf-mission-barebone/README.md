## NanoSat MO Framework - Mission: Barebone

This is the implementation of the Mission Barebone. It is the simplest possible implementation of the NanoSat MO Framework.

This project can be used for testing purposes of the NMF features at runtime.

### Building

Invoke `mvn clean install` in the main directory.

### Generating the deployable filesystem

The runnable *Space File System* — the directory a Supervisor is started from — is
generated by the `barebone-space-filesystem` module. Build the framework first
(see *Building* above) so its artifacts are available, then, from that directory:

```
mvn package -Pgenerate-filesystem
```

The result is written to `target/space-filesystem/nanosat-mo-framework/`; run the
Supervisor with `./start_supervisor.sh` from there.

Choose how apps are isolated with `-Dgenerate-filesystem.appsIsolation=<mode>`,
where `<mode>` is `none` (default), `linux-userspace`, `bubblewrap`, or
`docker-containers` (each app is launched in its own container).

### Running in Docker

**Prerequisite:** a container runtime must be installed — Docker or Podman. To
install Docker and be able to run it without `sudo`:

```
sudo apt-get install -y docker.io docker-buildx
sudo usermod -aG docker $USER   # then log out and back in for this to take effect
```

`docker-buildx` is optional today but recommended: Ubuntu's `docker.io` package
does not bundle it, so without it `docker build` falls back to the legacy builder
and prints a deprecation warning. The build still succeeds, but the legacy builder
is slated for removal, after which BuildKit (driven by buildx) becomes the only
builder. (Docker's own `docker-ce` packages already bundle buildx, so this note
only applies to the distro `docker.io` package above.)

Build the image from the `barebone-space-filesystem` directory. Either build the
filesystem first and then the image:

```
mvn package -Pgenerate-filesystem
docker build -t nmf-mission-barebone .
```

or do both in one step with the `docker` profile:

```
mvn install -Pdocker
```

Then run it. On Linux, use host networking, because the Supervisor advertises its
Directory URI with the container's own address — an external consumer (e.g. the
Consumer Test Tool) can only reach it if that address is routable:

```
docker run --network host nmf-mission-barebone
```

With bridge networking (`docker run -p 1024:1024 nmf-mission-barebone`) the port is
published, but a consumer receives the container's internal address in the
Directory response and cannot connect back until the advertised host is overridden.

Notes:

- **Podman**, or a `docker`/`podman` binary that is not on the `PATH`:
  `mvn install -Pdocker -Ddocker.executable=podman` (or a full path).
- The runtime base image defaults to `eclipse-temurin:21-jre`; so does the
  per-app image used by the `docker-containers` isolation mode
  (override with `-Desa.mo.nmf.packagemanager.docker.image=<image>`).

### Deploying to a remote machine

The generated filesystem can be uploaded to a remote target over scp with the
`deploy-on-remote` profile (self-contained — it generates the filesystem too):

```
mvn install -Pdeploy-on-remote -Ddeploy.remote.url=scp://user@host/
```

SSH credentials come from your `~/.ssh` / an ssh-agent, or from a `<server>` entry
in `settings.xml` matching the host.
