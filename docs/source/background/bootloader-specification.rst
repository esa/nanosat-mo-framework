==============================
NMF Bootloader Specification
==============================

This document specifies the NMF Bootloader: the component that starts the NanoSat MO Supervisor, selects
which software baseline to run, verifies its integrity, detects start-up failures and falls back to a
known-good baseline. It replaces the plain launcher script (``start_supervisor.sh``) generated by the
``nmf-linux-maven-plugin``.

The NMF Bootloader takes into consideration the **SAVOIR Flight Computer Initialisation Sequence Generic
Specification** (SAVOIR-GS-002). The correspondence between the two — the boot-chain layering, terminology
mapping, compliance matrix and deviations — is documented separately in :doc:`savoir-gs-002-mapping`.

.. note::

   Implementation status: this is a forward-looking specification. The bootloader described here is not yet
   implemented; the current ``start_supervisor.sh`` performs a plain JVM launch with no baseline selection,
   integrity testing or fallback.

Design overview
---------------

NMF Software baselines
~~~~~~~~~~~~~~~~~~~~~~

A *NMF Software Baseline* is the combination of a framework version, a mission software version and a Java
runtime, materialised as versioned directories: ``jars-nmf/<nmf-version>/`` (the framework JARs) and
``jars-mission/<mission-version>/`` (the mission-specific JARs, including the Supervisor implementation)
— each accompanied by a checksum manifest of its files — plus ``java/<jre-version>/`` (or the system Java
runtime). The components form one unit: falling back to an older framework version also restores the
mission version and the Java runtime it was validated with. For each baseline the manifest also records
the Supervisor main class, so that no version- or mission-specific value is baked into the bootloader
itself. Multiple versions coexist on disk. Three baselines have named roles, declared in the *baseline
manifest* file:

- **primary** — the baseline designated to run;
- **secondary** — the last confirmed-good baseline, rotated automatically when an upgrade is confirmed;
- **factory** — the baseline the mission was deployed with at integration time, immutable in flight.

The baseline manifest is the single source of boot configuration. It is written by three actors: the
Package Management service rotates primary/secondary automatically on a confirmed upgrade; ground can set the
*primary* and *secondary* fields directly through the Parameter service (validated before acceptance); the
*factory* field is written once at integration time. The bootloader itself only reads it.

The Java runtime is itself upgradeable in flight: the NMF Package format defines the ``java`` package type
for delivering JREs, installed under ``java/<jre-version>/``.

The shared application libraries (``jars-shared-libraries/``) are not part of the baseline: they are
dependencies of the NMF Apps, managed by the Package Management service, and are not covered by the
fallback ladder.

Boot sequence
~~~~~~~~~~~~~

On every start of the Supervisor — OS boot, manual start, or restart after a failure — the bootloader
executes the Nominal Sequence:

1. **Initialisation** — resolve the NMF root directory and start the Boot Report;
2. **Self-tests** — check the baseline-independent environment: directories, disk space;
3. **Baseline selection** — choose the baseline to run, from the baseline manifest and the fallback state;
4. **Integrity test** — verify the selected baseline: JAR checksums (SHA-256) and Java runtime launch
   check;
5. **Execution** — start the Supervisor from the selected baseline, capturing its output to the supervisor
   log;
6. **Confirmation** — wait for the Supervisor's boot confirmation marker; on failure, record the failed
   attempt and restart the sequence, where Baseline selection applies the fallback ladder
   (primary → secondary → factory).

Self-test and integrity-test failures do not stop the sequence: they are recorded in the Boot Report and
the boot proceeds, because a degraded environment or a checksum mismatch does not necessarily prevent the
Supervisor from running. There is a single recovery path: a boot that fails for any reason is caught by
the Confirmation step, and the fallback ladder decides what to try next.

Fail-safe mechanism: Failure detection and fallback
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

After launching the JVM, the bootloader waits for the Supervisor to confirm a successful start-up by
writing a *boot confirmation marker* once its services are up. A boot attempt is declared failed when the
JVM process exits, or when the marker has not appeared within ``BootConfirmTimeout``.

Failed attempts are counted in a runtime state area (separate from the baseline manifest). The fallback
ladder is: after ``BootMaxAttempts`` consecutive failures of the **primary** baseline, the bootloader boots
the **secondary** baseline; after ``BootMaxAttempts`` consecutive failures of the secondary baseline, it boots the
**factory** baseline. Every fallback decision is recorded in the Boot Report. Right after deployment the
three roles point at the same baseline and the ladder degenerates gracefully.

Boot Report
~~~~~~~~~~~

Each boot attempt produces a *Boot Report*, written step-by-step as the sequence progresses, so that a
crash mid-sequence leaves a report filled up to the failing step. Following the NMF logging convention
(one ISO-dated file per day, as for the Supervisor and App logs), the reports of a day are appended to a
daily file under ``logs/bootloader/``; each report is a timestamped section opened by a start marker and
closed by a completion marker, so a truncated report is distinguishable from a complete one. All files are
retained — the bootloader never deletes them. The only bound is the daily file size cap
(``MaxReportFileSize``), which only a persistent failure loop can reach: further reports of the day are
then suppressed after a notice, preserving the first — most diagnostic — reports of the day. Once the
Supervisor is running, the reports are retrievable from ground through its services.

Restart types
~~~~~~~~~~~~~

There are two restart types:

1. **Cold restart** — an OS boot;
2. **Warm restart** — a Supervisor restart without an OS reboot.

The sequence is the same for both.

Parameters
----------

The bootloader behaviour is governed by the following parameters. The parameter names follow SAVOIR-GS-002
section 9.3 (see :doc:`savoir-gs-002-mapping`); the ones marked *(NMF extension)* are NMF additions.

.. list-table::
   :header-rows: 1
   :widths: 22 78

   * - Parameter
     - Value in the NMF
   * - ``ColdWarm``
     - Cold restart = OS boot; warm restart = Supervisor restart without OS reboot. The sequence is the
       same for both. Detected by comparing the kernel boot identifier
       (``/proc/sys/kernel/random/boot_id``) with the one recorded in the runtime state area by the
       previous run; a missing record reports cold.
   * - ``FastBootPath``
     - Not supported. The Supervisor is not in the spacecraft's reconfiguration chain, so there is no
       boot-time criticality to justify skipping tests: the self-tests take milliseconds, the integrity
       test seconds, and the dominant cost (JVM start-up) cannot be skipped at all.
   * - ``NumberASWimages``
     - Three named baselines, a baseline being the combination {framework version, mission version, Java
       runtime}: *primary* (the baseline designated to run), *secondary* (the last confirmed-good baseline, rotated
       automatically on upgrade) and *factory* (the baseline the mission was deployed with at integration
       time, immutable in flight). Additional versions may be present on disk.
   * - ``IntegrityCheck``
     - SHA-256 checksums over every file of the baseline's two JAR directories, stored as a ``SHA256SUMS``
       file (``sha256sum -c`` format) inside each versioned directory. The Java runtime is verified
       functionally (NMF.BOOT.BTE.03), not by checksum.
   * - ``MaxReportFileSize`` *(NMF extension)*
     - Size cap of a daily report file: 100 KB (configurable). When exceeded, a suppression notice is
       written and further report sections of that day are skipped, preserving the first reports of the
       day.
   * - ``CriticalPMfunctions``
     - Critical: Java runtime, baseline manifest readability. Non-critical: log duplication to file
       (``tee``), disk-space check.
   * - ``BootConfirmTimeout`` *(NMF extension)*
     - Time the bootloader waits for the Supervisor's boot confirmation marker before declaring the boot
       attempt failed. Default: 60 s.
   * - ``BootMaxAttempts`` *(NMF extension)*
     - Consecutive failed boot attempts of a baseline before falling back to the next rung of the ladder.
       Default: 2.

Requirements
------------

Requirement identifiers follow the pattern ``NMF.BOOT.<Function>.<Number>``, keeping the SAVOIR function
acronyms (BEF: Boot Execution Flow, BIN: Boot INitialisation, BTE: Boot TEsts, BAA: Boot Actions After
tests, BMM: Boot Memory Management, IMP: IMPlementation); the ``REC`` function is an NMF extension. The
numbering is the NMF's own: traceability to the SAVOIR requirements is given by the *Traces to* field of
each requirement and by the compliance matrix in :doc:`savoir-gs-002-mapping`.

Boot execution flow (BEF)
~~~~~~~~~~~~~~~~~~~~~~~~~

**NMF.BOOT.BEF.01 — Single entry point.** The bootloader shall be the single entry point for starting the
Supervisor, executed on every start: OS boot, manual start, and restart after failure.

  :Traces to: SAVOIR.BOOTSW.BEF.10

**NMF.BOOT.BEF.02 — Nominal Sequence.** The bootloader shall execute as minimum the following steps:

1. **Initialisation** — resolve the NMF root directory and start the Boot Report;
2. **Self-tests** — check the baseline-independent environment (NMF.BOOT.BTE.01);
3. **Baseline selection** — choose the software baseline from the manifest (NMF.BOOT.BEF.03);
4. **Integrity test** — verify the selected baseline (NMF.BOOT.BTE.02, BTE.03);
5. **Execution** — start the Supervisor from the selected baseline;
6. **Confirmation** — wait for the Supervisor's boot confirmation (NMF.BOOT.REC.01, REC.02); on failure
   the sequence restarts and the Baseline selection step applies the fallback ladder (NMF.BOOT.REC.03).

  :Traces to: SAVOIR.BOOTSW.BEF.20
  :Note: SAVOIR step 1 (Processor Module Initialisation) is owned by the operating system; what remains
     for the bootloader is locating itself and opening the Boot Report, which must happen first so that
     the subsequent steps can be recorded (NMF.BOOT.BAA.03).
  :Note: the Confirmation step has no SAVOIR counterpart: the SAVOIR sequence ends at ASW execution
     because start-up failure recovery belongs to the hardware watchdog and Reconfiguration function; in
     the NMF the bootloader implements that role in software (see the REC requirements).

**NMF.BOOT.BEF.03 — Baseline selection.** The bootloader shall select the baseline to execute based on
configuration data (the baseline manifest, declaring the *primary*, *secondary* and *factory* baselines, each
the combination of a framework version, a mission version and a Java runtime) set prior to the start.

  :Traces to: SAVOIR.BOOTSW.BEF.25

**NMF.BOOT.BEF.04 — Sequence continuation on failure.** The bootloader shall execute the steps of the
Nominal Sequence also in case of failure in the self-tests or in the integrity tests, recording the
failures in the Boot Report.

  :Traces to: SAVOIR.BOOTSW.BEF.30
  :Rationale: as in SAVOIR, a self-test failure does not imply the Supervisor cannot run — nor does a
     checksum mismatch (the corrupted file may never be loaded). Attempting the execution anyway keeps a
     single recovery path: any actual start-up failure is caught by the Confirmation step (NMF.BOOT.REC.02)
     and handled by the fallback ladder; FDIR beyond baseline fallback is the Supervisor's responsibility.

Initialisation (BIN)
~~~~~~~~~~~~~~~~~~~~

**NMF.BOOT.BIN.01 — Known execution configuration.** The execution configuration handed to the Supervisor
shall be fully determined by the selected baseline and the NMF configuration files, and shall not depend
on how the bootloader itself was invoked (inherited environment variables, working directory, umask). The
classpath shall be derived exclusively from the two JAR directories of the selected baseline.

  :Traces to: SAVOIR.BOOTSW.BIN.250
  :Rationale: the bootloader is started both by the OS at boot and manually by an operator; the Supervisor
     must not behave differently between the two. The classpath exclusivity keeps anything outside the
     selected baseline — shared application libraries, leftover directories — from reaching the
     Supervisor's classpath.

Self-tests (BTE)
~~~~~~~~~~~~~~~~

**NMF.BOOT.BTE.01 — Environment self-tests.** The bootloader shall test the baseline-independent execution
environment: required directories present and writable; free disk space above a configurable threshold.

  :Traces to: SAVOIR.BOOTSW.BTE.260, BTE.270
  :Note: the self-tests are baseline-independent because they run before the Baseline selection step; the
     selected baseline's Java runtime is verified in the Integrity test step (NMF.BOOT.BTE.03).

**NMF.BOOT.BTE.02 — Baseline integrity test.** The bootloader shall perform an integrity test on the
selected baseline before execution, verifying every file of the baseline's two JAR directories against the
checksum manifest stored inside each.

  :Traces to: SAVOIR.BOOTSW.BTE.300

**NMF.BOOT.BTE.03 — Java runtime test.** The bootloader shall verify that the Java runtime of the
selected baseline executes (e.g. reports its version) before executing the Supervisor.

  :Traces to: SAVOIR.BOOTSW.BTE.270
  :Rationale: the Java runtime is verified functionally rather than by checksum: a JRE tree is large and
     checksumming it at every boot would weigh on the boot-time budget, while a runtime that starts and
     reports its version is fit for the Execution step.

**NMF.BOOT.BTE.04 — Single integrity algorithm.** The bootloader shall use the same algorithm (SHA-256)
for all integrity tests.

  :Traces to: SAVOIR.BOOTSW.BTE.330

Actions after tests (BAA)
~~~~~~~~~~~~~~~~~~~~~~~~~

**NMF.BOOT.BAA.01 — Critical functions.** The bootloader shall use critical functions (Java runtime,
baseline manifest) independently from the result of the related self-test; if a critical function fails,
the boot attempt fails and the reconfiguration logic (REC) applies.

  :Traces to: SAVOIR.BOOTSW.BAA.350

**NMF.BOOT.BAA.02 — Non-critical functions.** The bootloader shall use non-critical functions (log
duplication, disk-space check) only if the related self-test succeeded; a non-critical failure shall never
prevent the execution of the Supervisor.

  :Traces to: SAVOIR.BOOTSW.BAA.360

**NMF.BOOT.BAA.03 — Boot Report.** The bootloader shall write the result of each step of the sequence in
the Boot Report immediately after the execution of that step.

  :Traces to: SAVOIR.BOOTSW.BAA.370, BAA.390
  :Rationale: if the bootloader fails mid-sequence, the Boot Report is filled up to the failing step,
     allowing the failure to be correlated to the sequence step.

**NMF.BOOT.BAA.04 — Boot Report content.** As a minimum, the Boot Report shall include: timestamp,
cold/warm restart indication, the selected baseline and its
framework, mission and Java runtime versions, the secondary and factory baseline versions, the result of each
self-test and integrity test, any reconfiguration decision, and any error detected.

  :Traces to: SAVOIR.BOOTSW.BAA.385

**NMF.BOOT.BAA.05 — Boot Report integrity.** The Boot Report shall carry an explicit completion marker so
that a complete report can be distinguished from a truncated one.

  :Traces to: SAVOIR.BOOTSW.BAA.420

**NMF.BOOT.BAA.06 — Boot Report retention.** The bootloader shall retain all Boot Reports, appended per
boot attempt as timestamped sections of a daily report file. A daily file that exceeds
``MaxReportFileSize`` receives a single suppression notice and no further report sections that day. The
bootloader shall not delete Boot Report files.

  :Traces to: SAVOIR.BOOTSW.BAA.430, BAA.440
  :Rationale: a daily file only exists for days with boot attempts and is a few KB in nominal operation;
     the size cap only engages in a persistent boot failure loop, bounding growth to
     ``MaxReportFileSize`` per day while inherently preserving the first reports of each day — the ones
     SAVOIR notes are likely to contain the root cause, the later reboots being cascade effects. The cap
     is a plain file-size check, without parsing report content. Disposal of old reports is an
     operational activity, outside the bootloader.

Reconfiguration (REC) — NMF extension
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

**NMF.BOOT.REC.01 — Boot confirmation.** The Supervisor shall confirm a successful start-up by writing a
boot confirmation marker once its services are up. This is the software equivalent of the watchdog kick
described in SAVOIR-GS-002 section 4.1.1.

**NMF.BOOT.REC.02 — Failure detection.** The bootloader shall declare a boot attempt failed when the JVM
process exits, or when the boot confirmation marker has not appeared within ``BootConfirmTimeout``.

**NMF.BOOT.REC.03 — Fallback ladder.** After ``BootMaxAttempts`` consecutive failed boot attempts of the
primary baseline, the bootloader shall select the secondary baseline for the subsequent attempt; after
``BootMaxAttempts`` consecutive failed boot attempts of the secondary baseline, the bootloader shall select the
factory baseline.

**NMF.BOOT.REC.04 — Baseline rotation.** On the first confirmed boot of a newly installed baseline, the
previously primary baseline shall become the secondary baseline and the manifest updated accordingly.
This is performed at ASW level by the Package Management service, not by the bootloader.

**NMF.BOOT.REC.05 — Reconfiguration traceability.** Every reconfiguration decision (failed attempt count,
fallback to secondary or factory) shall be recorded in the Boot Report.

Storage (BMM)
~~~~~~~~~~~~~

**NMF.BOOT.BMM.01 — Bootloader isolation.** The bootloader and the baseline manifest shall reside outside
the versioned baseline directories; the installation, upgrade or removal of baseline components shall not
modify the bootloader.

  :Traces to: SAVOIR.BOOTSW.BMM.100, BMM.110
  :Rationale: mirrors the SAVOIR rationale for boot memory: a failed or corrupted update must not be able
     to take down the component that recovers from it.

**NMF.BOOT.BMM.02 — Manifest control.** The baseline manifest shall be commandable from ground. The
*primary* and *secondary* fields shall be settable, and a set shall be validated before acceptance: the
requested versions must be installed on disk and pass their integrity tests. The bootloader shall only
read the manifest.

  :Traces to: SAVOIR.BOOTSW.BEF.27
  :Note: in the NMF, the manifest is updated automatically by the Package Management service on a
     confirmed upgrade (REC.04), and its fields are exposed through the Parameter service for direct
     commanding (e.g. a manual rollback to the secondary baseline) — the NMF analogue of the SAVOIR
     direct-TC/HPC-1 override path: ground must always be able to choose the baseline to be loaded,
     independently of the package operations.
  :Note: automatic rotation (REC.04) preserves the invariant that the secondary baseline has booted
     successfully on the system at least once; a manual override of the secondary takes ownership of that
     invariant. The read-only *factory* field is covered by NMF.BOOT.BMM.03.

**NMF.BOOT.BMM.03 — Factory baseline immutability.** The components of the factory baseline, their
checksum manifests and the *factory* field of the baseline manifest shall not be modified in flight; the
Package Management service shall reject any install, upgrade or uninstall operation targeting them.

  :Traces to: SAVOIR.BOOTSW.BEF.20 (note), BMM.110
  :Rationale: implements the SAVOIR "untouched image to be used in case of contingency"; the factory
     baseline is the last rung of the fallback ladder and must be beyond the reach of in-flight software
     maintenance.

**NMF.BOOT.BMM.04 — Baseline independence.** The bootloader shall be independent from the actual values of
the baseline (version strings, file lists, sizes); all baseline knowledge comes from the baseline manifest
and the per-directory checksum manifests.

  :Traces to: SAVOIR.BOOTSW.BMM.120

**NMF.BOOT.BMM.05 — Boot Report storage.** Boot Reports shall be stored in ``logs/bootloader/``, distinct
from the Supervisor logs (``logs/supervisor/``); the Supervisor shall not write to the Boot Report area
except for the boot confirmation marker.

  :Traces to: SAVOIR.BOOTSW.BMM.130, BMM.140, BMM.170

Implementation (IMP)
~~~~~~~~~~~~~~~~~~~~

**NMF.BOOT.IMP.01 — Simplicity.** The bootloader shall be a sequential POSIX shell script with no
background processes, requiring only a POSIX shell, coreutils, ``sha256sum`` and the Java runtime.

  :Traces to: SAVOIR.BOOTSW.IMP.460, IMP.470
  :Rationale: SAVOIR requires OS independence because the Boot SW predates the OS; on the NMF the OS is a
     given, so the spirit is kept instead: minimal, sequential, no runtime machinery, trivially reviewable.
